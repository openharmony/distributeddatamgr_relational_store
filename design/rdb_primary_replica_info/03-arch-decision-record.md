# 方案选型决策评审（Decision）

## 1. 背景与问题

新增 Native C++ 主备信息接口，需要选择由主连接持有备库句柄还是采用独立诊断连接。需求依据见 [01-requirement.md](01-requirement.md)，可行性与工作量依据见 [02-feasibility.md](02-feasibility.md)，静态事实见 [代码证据](_draft/code-evidence.md)。

硬约束：仅 Native 内部接口，支持两种现有主备模式及已有加密能力；回放和 checkpoint 前采集毫秒时间，之后采集 DB/WAL 大小和可选普通表精确行数；允许并发采样，保留部分结果及失败，不主动恢复或重建，保持存量接口兼容。

用户已明确本需求实现允许修改源码；可在当前 feature/mock-test-fixes 分支实施并保留已有变更。正式归档信息暂缓，本文只供接口行为和技术选型参考，不表示 SIG 已评审，也不设置性能指标。

## 3. 候选方案（决策矩阵）

| 方案 | 优势 | 劣势 | 成本 | 风险 | AI推荐倾向 |
|------|------|------|------|------|-----------|
| A：复用主连接已有备库句柄，Store 编排诊断；无句柄时跳过依赖句柄的操作 | 复用既有句柄和配置，保持既有主备持有关系；无需独立 temps_ 连接 | 无备库句柄时无法执行备库 checkpoint、计数及主备回放 | 生产代码估算 600～900 行；开发 1.2～1.8 人月；端到端 1.68～2.52 人月 | 严格使用真正备库句柄，验证句柄寿命；逐项表达跳过和失败，绕开损坏删除分支 | 工程倾向 A：复用现有连接，接受缺句柄时的部分结果；用户选择记于 §5 |

### 共同候选接口职责

接口名和返回类型仍是设计草案，选型后细化。RdbStore 新入口可采用 `GetPrimaryReplicaInfo`，输出两库 DB/WAL 大小、归纳时间、可选 64 位行数，以及各字段/操作的状态；Connection 输出 DB/WAL/binlog 三种原始时间，提供细粒度操作，Store 负责流程编排和归纳。

| 草案操作 | 所属层及职责 |
|----------|---------------|
| `CaptureFileTimes(role, out)` | Connection 采集 DB/WAL/binlog 原始时间及逐项状态；在回放和 checkpoint 前调用 |
| `ReplayForInspection(out)` | Connection 尝试已有 binlog 回放，保留可观察状态，不调用恢复/重建路径 |
| `CheckpointForInspection(role, out)` | Connection 明确目标库并分别返回主备状态，不附带损坏库删除 |
| `CaptureFileSizes(role, out)` | Connection 在维护尝试之后采集 DB/WAL 大小，区分缺失与采集失败 |
| `CountForInspection(role, table, out)` | Connection/Statement 对真正目标库执行普通表精确计数，验证并引用表名，读取 64 位标量 |

Store 先保存全部可获取的原始时间，再复用已有备库句柄、尝试回放、分别 checkpoint、采集大小与可选行数，最后聚合部分结果。无备库连接时不尝试打开，跳过依赖备库句柄的操作；不调用带删除/重建分支的 `InnerOpenSlave`。主库归纳时间只取 DB/WAL 较大值；备库有其关联 binlog 时取最新 binlog 时间，否则取备库 DB/WAL 较大值。扫描失败须保留失败状态，不能等同确定没有日志；日志时间不证明备库已经应用日志。

### 候选改动范围

| 层/路径 | A | B |
|---------|---|---|
| inner_api 的 RdbStore 类型与 RdbStoreImpl | 新入口、结果结构、按序编排及时间归纳 | 共同能力，增加受管诊断连接获取与释放编排 |
| Connection、SqliteConnection、Statement | 细粒度诊断操作；复用主连接持有的已有备库句柄，缺句柄时跳过依赖操作；文件采集与有状态维护，传递既有加密/VFS 配置 | 共同采集与维护能力，安全策略用于独立诊断连接 |
| ConnectionPool | 获取和持有已有受管连接 | 扩展受管临时连接创建以承载诊断策略，纳入 temps_ |
| 默认后端、构建和单测 | 非 SQLite 默认不支持；同步编译清单；验证主备来源、时间顺序、部分失败、缺句柄跳过、文件缺失和并发句柄寿命 | 共同验证，额外覆盖独立连接配置及 temps_ 释放 |

两方案均保持 RdbStoreImpl → ConnectionPool → Connection → Statement 分层，不改变旧 `ReplayBinlog`、`TryCheckPoint` 或 `CreateReplicaStatement` 的语义，也不新增 JS/ETS/NDK 绑定。损坏、忙、无句柄等结果须逐项保留；已有文件可采集不代表一定可执行 checkpoint 或计数。

## 5. 决策结果与理由

选定方案：A，复用主连接已有的备库连接；没有连接时不尝试打开，跳过依赖备库句柄的回放、checkpoint 和计数，返回主库可用信息。

用户原选择：“A：复用现有主备连接（推荐，接受缺句柄时的部分结果）”。选项表达的理由为复用现有连接、接受部分结果，不另补推断理由。

决策者：本次对话用户。本记录仅反映用户选择，不宣称 SIG 已评审或完成正式签核。
